# Poseidon-over-BLS12-381 Constants Provenance

This document consolidates the provenance, verification status, risk model, and mitigation strategy for the Poseidon hash function constants and parameters used over the BLS12-381 scalar field ($F_r$) in Sharibo.

---

## 1. Package & Version Specification

Circom's default `circomlib` implementation provides Poseidon constants hardcoded specifically for the **BN254** (alt_bn128) scalar field. Because Sharibo runs natively on Stellar's accelerated **BLS12-381** curve, separate Poseidon round constants and MDS (Maximum Distance Separable) matrices tailored to the BLS12-381 scalar field are required.

Sharibo uses the following third-party package pair authored by `@jmagan`:

| Layer | Package Name | Version | Usage Site | Primary Export / Template |
|---|---|---|---|---|
| **Circuits (Circom)** | [`poseidon-bls12381-circom`](https://github.com/jmagan/poseidon-bls12381-circom) | `1.0.0` | `circuits/membership.template.circom` | `Poseidon255(2)` |
| **Client (TypeScript)** | [`poseidon-bls12381`](https://github.com/jmagan/poseidon-bls12381) | `1.0.2` | `packages/client/src/identity.ts` | `poseidon2([a, b])` |

## 2. Verification Status

### What Was Verified

1. **Modulus Cross-Check ($F_r$)**:
   - The hardcoded scalar field prime modulus in both packages:
     $$\text{Modulus} = \text{0x73eda753299d7d483339d80809a1d80553bda402fffe5bfeffffffff00000001}$$
     ($52435875175126190479447740508185965837690552500527637822603658699938581188469$)
   - Cross-checked directly against `soroban-sdk`'s native Rust constant (`BLS12_381_FR_MODULUS_BE`). An exact byte match confirmed that both packages target the exact BLS12-381 scalar field used on-chain by Soroban.

2. **Round Structure & Permutation Shape**:
   - Verified for arity $t = 3$ (2 inputs + 1 state element):
     - **Full Rounds ($R_F$)**: 8 (4 full rounds at start, 4 at end)
     - **Partial Rounds ($R_P$)**: 56
     - **S-Box Exponent**: $x^5$ ($\text{gcd}(5, r-1) = 1$)
   - This matches the recommended parameter configuration from the official Poseidon paper for security against algebraic attacks over BLS12-381.

3. **Cross-Implementation Consistency**:
   - The round constants and MDS matrix entries in the Circom circuit implementation (`poseidon255_constants.circom`) were verified against the TypeScript client implementation (`poseidon2.ts`).
   - Verified programmatically and enforced via shared cross-implementation test vectors in `test-vectors/poseidon.json`.

---

### What Was NOT Verified

1. **Independent Constant Generation**:
   - The round constants and MDS matrix entries were **not** independently generated from scratch using the reference Grain-LFSR script.
2. **Independent Cryptographic Audit**:
   - Neither `poseidon-bls12381` nor `poseidon-bls12381-circom` has undergone a formal third-party security audit.

---

## 3. Risk Analysis

- **Malicious or Weak Constants**:
  - If round constants or the MDS matrix contained an intentional trapdoor or were generated with weak randomness, an attacker aware of the vulnerability could potentially compute hash collisions or invert the Poseidon permutation.
  - *Impact*: In Sharibo, this could allow an attacker to forge Merkle membership proofs or duplicate nullifiers, compromising privacy or draining circle funds.
- **Implementation Divergence Risk**:
  - If circuit and client constants differed, valid proofs generated by honest users would fail verification on-chain. (Mitigated by test vector verification).

---

## 4. Planned Mitigation & Roadmap

1. **Self-Generated Constants**:
   - Re-run the reference Grain-LFSR parameter generator for BLS12-381 with full transparency, publishing the exact seed parameters, generation scripts, and transcripts.
2. **Third-Party Security Audit**:
   - Commission an independent audit of the BLS12-381 Poseidon parameters, circuit constraints, and client implementations prior to production deployment.
